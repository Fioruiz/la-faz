# CLAUDE.md – Sistema de donaciones y control de proyectos (ONG La FAZ)

## 1. Contexto del proyecto

### Qué es
Una aplicación web única para la ONG **La FAZ**, con dos zonas sobre la misma base de datos:

- **Zona pública**: presenta la ONG y sus proyectos, muestra la barra de avance de las metas (por ejemplo, "1200 de 2000 packs"), explica cómo donar y ofrece un formulario de voluntariado.
- **Zona privada** (login para ~3 responsables): crea proyectos con metas por ítem, registra donaciones en dinero o en producto, muestra el avance, lleva el registro de apoyantes y voluntarios, y da un reporte en pantalla.

El detalle completo de funciones, exclusiones y criterios de éxito está en `PRD.md`. Ese archivo es la fuente de verdad.

### Qué problema resuelve
La ONG no tiene un canal oficial de donaciones ni un control centralizado. Los donantes depositan en cuentas personales de responsables, y el registro vive en un cuaderno o en un WhatsApp personal. Nadie sabe con certeza cuánto se recaudó ni cuánto falta para cada meta, y los donantes extranjeros desconfían de una ONG sin web oficial.

### Contexto del negocio
- La FAZ es una asociación sin fines de lucro que acompaña a personas, familias y comunidades en situación de vulnerabilidad, en Perú (Ventanilla (Callao), Chepén e Ica).
- Proyectos: **10 Derechos** (cada noviembre, con packs para niños; meta de ejemplo: 2000 niños = 2000 packs), **Apoyo alimentario** (canastas básicas para familias en pobreza y pobreza extrema), **Música** (niños, adulto mayor y damnificados) y **Casa del Buen Samaritano**.
- Las donaciones llegan por transferencia, Yape y Plin, y en producto (agua, cereal, fruta, etc.). El efectivo casi no se usa.
- Al inicio solo 10 Derechos y Apoyo alimentario tienen meta y barra de avance. Música y Casa del Buen Samaritano son informativos.
- Es un **proyecto real, sin cobros**: los datos de donantes y voluntarios son reales, pero el sistema no cobra ni hace transacciones bancarias. La cuenta bancaria y los pagos internacionales son una demo o simulación. No se justifica una decisión de seguridad con "es solo una prueba".
- Prioridad: primero el control interno (registrar y ver avance). La web pública muestra esos mismos datos.

### Arquitectura general
- **Una sola aplicación, una sola base de datos.** Lo que el responsable registra en la zona privada es lo que la zona pública muestra como avance.
- Usuarios: responsables (con login), donantes y voluntarios (sin cuenta).
- Entidades principales: proyecto, ítem con meta, donación (dinero o producto), apoyante (donante o voluntario) e historial de cambios.
- Stack decidido en `TECH-DESIGN.md` y `adrs/` (greenfield): Next.js (App Router) + TypeScript + Tailwind, Server Actions como contrato (sin API REST), Drizzle con `@neondatabase/serverless` sobre Postgres en Neon, y Auth.js con credenciales. Debe poder desplegarse en Vercel free tier.
- Reglas de arquitectura que hay que respetar (detalle en los ADR):
  - El avance de un ítem se calcula siempre con `SUM` de donaciones **en producto** no anuladas; no se guardan contadores. El dinero va aparte y solo suma a un total en soles por proyecto (ADR 0002).
  - Toda escritura es una Server Action que valida con Zod, comprueba que el responsable esté activo y guarda el cambio y su `audit_log` en una sola transacción (ADR 0003, 0006).
  - Las páginas no usan caché: cada visita consulta Postgres (ADR 0005).
  - Las páginas públicas leen solo desde el módulo de lecturas públicas (`lib/public-queries.ts`), nunca tablas directas, para no filtrar datos personales ni donaciones "Sin asignar" (ADR 0007).

## 3. Comandos del entorno

Estos comandos son los scripts reales de `package.json` (confirmados con el andamiaje, #1).

```bash
# Ubicación del proyecto
cd /Users/stephanie/Documents/DIPLOMADO/CURSO-IA/PROYECTO-FINAL

npm install        # instalar dependencias
npm run dev        # servidor de desarrollo (Next.js)
npm run build      # build de producción
npm run start      # servir el build de producción en local

# Base de datos (Drizzle + Neon)
npm run db:check         # prueba la conexión (select 1 y transacciones)
npm run e2e             # pruebas E2E con Playwright (e2e/): arrancan la app en :3200 contra la rama de PRUEBAS de Neon (scripts/e2e-servidor.ts se niega si apunta a la real); `e2e/donacion.spec.ts` crea un responsable, un donante y una donación para 10 Derechos EN LA RAMA DE PRUEBAS y lo borra al terminar (nunca producción); el test del formulario vacío limpia los contadores de límite de esa rama. Con `E2E_REUTILIZAR=1` reutiliza una app ya levantada con `scripts/e2e-servidor.ts`
npm run db:generate      # genera la migración SQL en drizzle/ a partir de lib/schema.ts
npm run db:migrate       # aplica las migraciones a la base de .env.local (producción)
npm run db:seed          # carga los 4 proyectos iniciales (repetible)
npm run db:test          # migra la rama de pruebas y ejecuta las pruebas del esquema
npm run db:seed-responsable  # crea el responsable inicial (RESPONSABLE_INICIAL_*); repetible, no cambia a uno existente
npm run db:rol-publico -- --prueba   # crea/actualiza el rol de solo lectura de lo público en la rama de pruebas (PUBLICO_LECTURA_PASSWORD solo al crear o con --rotar); en producción exige --confirmar-produccion
```

- Las credenciales de base de datos (cadena de conexión a Neon) van en `.env.local`, que no se versiona ni se muestra en el chat. En Vercel se configuran como variables de entorno.
- Variables: `DATABASE_URL` (conexión pooled, la usa la aplicación), `DATABASE_URL_UNPOOLED` (conexión directa, la usan las migraciones) y `DATABASE_URL_TEST` en `.env.test` (rama `test-esquema` de Neon). Ninguna se versiona.
- `npm run db:test` nunca debe apuntar a producción: `DATABASE_URL_TEST` debe ser otro endpoint, y las pruebas abortan si coincide con el de producción. `db:migrate`, `db:seed` y `db:seed-responsable` sí escriben en producción; hay que confirmarlo con el usuario antes de ejecutarlos.
- Variables de acceso: `AUTH_SECRET` (firma de la sesión de Auth.js; distinto en local y en Vercel) y `RESPONSABLE_INICIAL_NOMBRE`, `RESPONSABLE_INICIAL_CORREO` y `RESPONSABLE_INICIAL_PASSWORD` (solo las lee `db:seed-responsable`; la contraseña lleva al menos 12 caracteres y se quita de `.env.local` después). Ninguna se versiona.
- Zona privada: toda lectura o escritura privada pasa por `requireResponsableActivo()` (`lib/private-access.ts`), que consulta a la base en cada petición (ADR 0009). Las páginas privadas viven en `app/(privado)/`, no importan la base ni el esquema, y nuevas consultas se añaden a `lib/private-queries-core.ts`. El `proxy.ts` solo redirige al login; no es la barrera de seguridad.
- Escrituras privadas: toda Server Action de escritura bajo `app/(privado)/` se crea con `crearAccionPrivada()` (`lib/escritura-auditada.ts`; el ejemplo de uso está en su encabezado). Comprueba al responsable activo, valida con Zod y guarda el cambio y su fila de `audit_log` en una sola transacción. La acción declara obligatoriamente su historial (`auditoria`, con solo los valores que deban quedar: nunca hashes ni datos que no corresponda guardar) y rechaza con `ReglaDeNegocioError("mensaje")`. Devuelve un `ResultadoAccion` (éxito, `validacion`, `regla` o `error`); un fallo inesperado muestra un mensaje genérico y el log solo lleva el tipo de error y su código. Una prueba estructural falla si una acción privada no usa el patrón.
- Proyectos e ítems (`app/(privado)/proyectos/`, `lib/proyectos-escrituras.ts`): los ítems solo existen en proyectos con meta y un proyecto con ítems no puede quedar sin meta; un proyecto finalizado es de solo lectura (ni él ni sus ítems se editan ni se reabren); no hay borrado de proyectos ni ítems (el PRD no lo menciona; si hace falta, actualizar el PRD primero); nombres únicos sin distinguir mayúsculas; el costo referencial es por UNA unidad del ítem. Cada escritura bloquea la fila del proyecto (`for update`) para no cruzarse con otra. La lógica de escritura vive sin Next en `lib/proyectos-escrituras.ts` y se prueba con `ejecutarEscrituraAuditada()`.
- Apoyantes (`app/(privado)/apoyantes/`, `lib/apoyantes-escrituras.ts`): datos personales mínimos, solo nombre, contacto de texto libre, roles (donante y/o voluntario) y la marca de anonimato; sin documentos de identidad ni direcciones. El contacto **no** va al `audit_log` ni a los logs (el historial guarda `tieneContacto` y `contactoModificado`), no aparece en la lista y solo se ve en el detalle. Los nombres no son únicos y los apoyantes no se borran ni se anonimizan a pedido (decisión del usuario; el PRD no lo menciona: si hace falta, actualizar el PRD primero). No se puede quitar un rol con registros asociados (donaciones o inscripciones). "Anónimo" sale de `nombrePublico()` (`lib/apoyantes-publico.ts`): las lecturas públicas de `lib/public-queries.ts` (#12) deben usarla y nunca el campo `nombre` directo. **Falta revisión legal** de la ley peruana de protección de datos personales (consentimiento, acceso, cancelación y retención); lo anterior es solo una medida mínima y el consentimiento queda para el formulario público de voluntariado (#13). #7 debe comprobar que el apoyante tenga el rol de donante.
- Donaciones (`app/(privado)/donaciones/nueva/`, `lib/donaciones-escrituras.ts`): `registrarDonacion` registra lo que el responsable DECLARA haber recibido (el sistema no cobra). Dinero: monto en soles y medio obligatorio (yape, plin, transferencia; se valida en la acción, la base no lo exige). Producto asignado: proyecto con meta e ítem de ese proyecto, sin medio ni monto. Producto "Sin asignar": sin proyecto ni ítem y con descripción. El proyecto debe estar activo y el apoyante debe tener el rol de donante; ambos se leen con `for share` para ordenarse con las escrituras que usan `for update` (finalizar proyecto, editar roles). Fecha por defecto y tope: hoy en America/Lima (`lib/fechas.ts`), no la del servidor (UTC). Aviso blando de duplicados (mismo donante, tipo, fecha, proyecto y monto, o ítem y cantidad, o descripción sin asignar): lanza `AdvertenciaError` → resultado `advertencia`, se confirma con `confirmarDuplicado`; no es atómico ni hay restricción única (ADR 0006). Donación mixta: la segunda apunta a la primera con `donacion_vinculada_id` (mismo donante, tipo distinto, ninguna ya en pareja). El historial guarda el id del donante, nunca su nombre ni contacto. Editar, anular y asignar donaciones es el ítem #8: hasta entonces un registro erróneo no se corrige desde la interfaz.
- Corregir donaciones (`app/(privado)/donaciones/`, `lib/donaciones-correcciones.ts`): se pueden editar monto, medio, fecha, cantidad, descripción y proyecto o ítem; el tipo y el donante NUNCA cambian (si estaban mal, se anula y se registra de nuevo; la escritura toma ambos de la fila, no de la entrada). Reasignar solo a proyectos activos con ítem del proyecto; asignar una "Sin asignar" es una operación aparte (`asignarDonacion`, una fila de historial `asignar`, borra la descripción libre y el historial conserva la anterior). Anular exige un motivo (hasta 200 caracteres) que va solo al historial, deja `anulada = true` y no se revierte; no hay borrado ni restaurar. Una donación anulada, o de un proyecto finalizado, es de solo lectura (pregunta abierta: cómo corregir las de un proyecto cerrado, que exigiría reabrirlo). Anular una parte de una donación mixta no anula la otra. Orden de bloqueos: la donación con `for update` y luego los proyectos implicados con `for share` por id ascendente. Las reglas compartidas con el registro (fecha, proyecto e ítem, duplicados) viven en `lib/donaciones-reglas.ts`; si una regla cambia, cambia ahí. Los formularios de editar usan `key` con los datos guardados para reiniciarse tras asignar o editar. `getDonacion`/`listarDonaciones` nunca devuelven el contacto.
- Avance (`lib/avance.ts` puro, `lib/avance-consulta.ts` con 3 consultas SQL fijas, `lib/dinero.ts`): ÚNICA función de avance, compartida con la zona pública; #12 (`lib/public-queries.ts`) debe reutilizar `consultarAvance()` y limitar la barra a 100% solo al presentar; no se copia la lógica ni se suma en las páginas. Recibido de un ítem = `SUM(cantidad)` de producto no anulado con ese ítem; el dinero nunca suma a una barra; las "Sin asignar" no cuentan en ningún proyecto; no hay contadores guardados. Falta en soles (ADR 0010) = `max(0, Σ ítems con costo de max(0, meta − recibido) × costo − dinero del proyecto)`: el excedente de un ítem no compensa a otro; `estimacion` es `completa`, `parcial` (hay algún ítem sin costo, literal del ADR) o `no-disponible` (ningún costo: no se muestra "S/ 0"). No hay porcentaje del proyecto (A3: se muestra por ítem más "N de M metas cumplidas"). Dinero siempre en céntimos con `BigInt` (`lib/dinero.ts`), nunca `float`; las cantidades sí son números. El bloque "Sin asignar" de `/proyectos` y `/proyectos/[id]` enlaza a `/donaciones?filtro=sin-asignar`.
- Reporte (`app/(privado)/reportes/`, `lib/reporte.ts` puro, `lib/reporte-consulta.ts` con 6 consultas SQL fijas, `getReporte()` en `lib/private-queries-core.ts`): dos vistas, por responsable (`registrado_por`, también desactivados, marcados) y por proyecto (con grupo "Sin asignar"). La regla de donación vigente vive solo en `lib/donaciones-condiciones.ts` y la comparten avance y reporte; sin filtro de fechas el reporte iguala al avance. Dinero en céntimos con `BigInt`, total con subtotales por medio (más "sin medio" si faltara, para que siempre sumen); productos por ítem y unidad sin mezclar, y los "sin asignar" en un renglón sin sumar cantidades. Las anuladas quedan fuera de los totales y se cuentan aparte con enlace a `/donaciones?filtro=anuladas`. El rango desde–hasta (fecha de la donación, inclusivo) viaja por GET y lo valida `validarRango()` (formato real, desde ≥ 2020-01-01, hasta ≤ hoy + 1 año, desde ≤ hasta). Sin nombres ni contactos de donantes (no toca `apoyantes`). Sin exportar a Excel, PDF o CSV (PRD: No alcance); una prueba estructural lo vigila.
- Sitio público estático (`app/(publico)/`, `lib/sitio-contenido.ts`): inicio, `/quienes-somos` (con la línea de tiempo `#historia`), `/como-donar` y `/voluntariado` (con el formulario de #13, ver abajo). Todo el texto, los datos legales y los datos de demostración viven en `lib/sitio-contenido.ts`; las páginas solo lo presentan, no importan la base ni nada privado y se prerenderizan como estáticas (no contradice el ADR 0005: no muestran avance; la página de proyectos de #12 sí debe ser dinámica y leer por `lib/public-queries.ts`). "Cómo donar" usa datos de cuenta ficticios (ceros, "Banco de Demostración") con aviso visible, sin formularios, botones ni SDK de pago; una prueba estructural (`tests/sitio-publico-estructura.test.ts`) lo vigila, y también que el menú no tenga enlaces rotos. El menú no tiene "Proyectos" hasta #12, que debe añadirlo, mostrar qué se puede donar (ítems de cada proyecto) y enlazar desde "Cómo donar". Ubicación de la ONG confirmada por el usuario: Ventanilla (Callao), Chepén e Ica. El color de marca (`--marca` en `app/globals.css`) es una propuesta: la ONG no entregó paleta ni logotipo. Un formulario público donde el donante registre datos NO existe ni está en el PRD (solo el de voluntariado, #13).
- Proyectos públicos (`app/(publico)/nuestros-proyectos/`, `lib/public-queries-core.ts` + `lib/public-queries.ts`): la URL es `/nuestros-proyectos` porque `/proyectos` es la lista privada (el menú público dice "Proyectos"). `lib/public-queries.ts` es la ÚNICA lectura de la zona pública (ADR 0007): 1 consulta de proyectos más `consultarAvance()` (4 en total, sin importar cuántas donaciones haya), proyectado a un tipo cerrado (`ProyectoPublico`/`ItemPublico`) sin dinero, costo referencial, "Sin asignar" ni datos de apoyantes; no lee `apoyantes` (si algún día se muestra un nombre, por `nombrePublico()`). El tope de la meta se aplica solo ahí, al presentar (2150 de 2000 se muestra como 2000 de 2000 al 100%; el excedente real es solo de la zona privada); el dinero no mueve ninguna barra ni se muestra, y no se muestra ningún donante (decisiones del usuario, C3). Páginas `force-dynamic` sin caché (ADR 0005); si la base falla, `error.tsx` (sin avance en cero ni datos técnicos); id inválido o inexistente da 404. Informativos solo con descripción; finalizados con su resultado y sin invitar a donar; con meta sin ítems, aviso "Pronto publicaremos qué se necesita". La descripción y el resultado de un proyecto son públicos (el formulario privado lo avisa). `tests/public-queries.test.ts` y `tests/public-estructura.test.ts` lo vigilan.
- Voluntariado (`app/(publico)/voluntariado/`, `lib/voluntariado-*.ts`, lista privada en `app/(privado)/voluntarios/`): es la ÚNICA escritura pública del sistema (excepción del ADR 0003 a "responsable activo"). `inscribirVoluntario()` (`lib/voluntariado-inscripcion-core.ts`, sin Next) sigue el orden campo trampa (`sitio_web`; si trae texto no guarda nada y responde el mismo éxito) -> Zod (nombre 100, contacto 200 obligatorio, mensaje 500, consentimiento obligatorio) -> una transacción que crea SIEMPRE un apoyante nuevo (voluntario, no donante, no anónimo) y su inscripción; nunca busca ni reutiliza apoyantes por contacto. No escribe en `audit_log` (`responsable_id` es obligatorio y quien se inscribe no es responsable): el registro es la propia fila (`creado_en` y `consentimiento_version`). La versión del consentimiento la fija el servidor desde `CONSENTIMIENTO_VOLUNTARIADO` (`lib/sitio-contenido.ts`), nunca el formulario; **el texto es provisional y falta la revisión legal** (ley peruana de protección de datos; derechos de acceso, cancelación y retención), y desde este ítem ya se guardan datos personales reales. Si falla la base, mensaje genérico y el log solo lleva tipo y código. Sin captcha ni límite por IP (ADR 0006): el spam o los repetidos los limpia a mano un responsable, y no hay anular ni borrar inscripciones (decisión previa; si hace falta, actualizar el PRD primero; #14 lo revisa). `/voluntarios` lista las 200 más recientes (nombre, fecha en Lima, mensaje como texto) SIN contacto, que solo se ve en `/apoyantes/[id]`; `listarVoluntarios()` vive en `lib/private-queries-core.ts` y el `proxy.ts` la cubre. `tests/voluntariado-*.test.ts` y `tests/public-estructura.test.ts` vigilan que ninguna lectura pública toque `apoyantes`.
- Endurecimiento (#14, ADR 0011; `lib/rol-publico.ts`, `lib/db-publico.ts`, `lib/limite-intentos.ts`, `scripts/crear-rol-publico.ts`): la zona pública lee SOLO con el rol de Postgres `publico_lectura` (`DATABASE_URL_PUBLICO`, obligatoria: sin ella la web pública falla de forma visible y NO cae a `DATABASE_URL`). El rol solo tiene `SELECT` sobre `proyectos`, `items_meta` y las columnas `id, proyecto_id, item_id, tipo, cantidad, monto, anulada` de `donaciones`; lo no listado en `lib/rol-publico.ts` queda denegado, y si `consultarAvance()` necesita una columna nueva hay que añadirla ahí y volver a ejecutar `db:rol-publico`. Solo `lib/public-queries.ts` importa `db-publico`. Límites con contadores en Postgres (`intentos_limitados`, clave = HMAC con `AUTH_SECRET`, nunca el correo ni la IP en claro): login máximo 5 intentos por correo en 15 minutos (se REGISTRA el intento antes de comprobar la contraseña y el sexto se rechaza; si se comprobara primero, peticiones en paralelo evadirían el tope; está en `autenticarResponsable()`, cubre la llamada directa a `/api/auth`; un correo inexistente cuenta igual; un acierto borra los intentos); formulario de voluntariado 5 envíos por hora por IP (`x-forwarded-for`; una IPv6 cuenta por su /64; el límite va ANTES del campo trampa y de validar, así que todo envío cuenta). Si el contador falla no se da acceso ni se guarda nada. Las pruebas del rol (`tests/rol-publico.test.ts`) necesitan `DATABASE_URL_TEST_PUBLICO` en `.env.test`. Respaldo por la restauración de Neon (`RESPALDO.md`). **No se migra producción ni se despliega hasta resolver `CHECKLIST-PUBLICACION.md`** (decisión del usuario): `db:migrate`, `db:rol-publico --confirmar-produccion` y el despliegue se confirman con el usuario uno a uno.
- El diseño técnico está en `TECH-DESIGN.md` y las decisiones en `adrs/`. Si una tarea contradice un ADR, se señala y se espera decisión, igual que con el PRD.
- Las skills del proyecto están en `.claude/skills/`. La del PRD es `generar-prd-conversacional`.
